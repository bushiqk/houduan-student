# 第 3 课　数据层：实体、关联、查询与事务

## 本课目标

1. 一个 Java 类怎么变成数据库里的一张表？`birthDate` 为什么对应 `birth_date`？
2. `@OneToMany`、`@ManyToOne`、`cascade`、`FetchType` 分别在控制什么？
3. `findByLastNameStartingWith` 为什么不用写 SQL？
4. 分页到底发生在数据库还是内存里？
5. 为什么这份代码能在 H2、MySQL、PostgreSQL 上跑，却在这里埋了一个坑？

预计用时 5-7 小时（含 4 个实验）。本课是后端开发的核心，请务必边看边打开 `h2-console`。

## 1. 实体映射：从 Java 对象到数据库表

继承链在 `src/main/java/org/springframework/samples/petclinic/model/` 下：

```java
@MappedSuperclass
public class BaseEntity implements Serializable {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    public boolean isNew() {
        return this.id == null;
    }

}
```

- `@MappedSuperclass`：不是一个独立实体、没有自己的表，只是把字段"下发给"子类。所以 `owners`、`pets`、`visits` 表里都有 `id`，但不存在 `base_entity` 表。
- `@Id` + `@GeneratedValue(IDENTITY)`：主键由数据库自增生成，对应建表脚本里的 `GENERATED BY DEFAULT AS IDENTITY` / `AUTO_INCREMENT`。
- `isNew()` 是贯穿全项目的判断依据："有没有 id"等同于"是不是还没入库的新对象"。`Owner.addPet`、`PetValidator` 都在用它。

`Person` 同理（`firstName`/`lastName` 映射给 `Owner` 和 `Vet` 复用），`Owner extends Person` 才有 `@Entity @Table(name = "owners")`。

**字段名和列名不一样，靠什么对上？** 靠 `application.properties` 里这一行：

```
spring.jpa.hibernate.naming.physical-strategy=org.hibernate.boot.model.naming.PhysicalNamingStrategySnakeCaseImpl
```

它把 Java 的驼峰命名自动转成数据库的下划线命名，所以 `birthDate` 不需要 `@Column(name = "birth_date")` 也能对到 `birth_date`。只有名字实在对不上时才要显式写，例如 `Visit` 里的：

```java
@Column(name = "visit_date")
private LocalDate date;
```

## 2. 关联关系：谁持有谁

`Owner`（一对多）：

```java
@OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
@JoinColumn(name = "owner_id")
@OrderBy("name")
private final List<Pet> pets = new ArrayList<>();
```

`Pet`（多对一 + 一对多）：

```java
@ManyToOne
@JoinColumn(name = "type_id")
private PetType type;

@OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
@JoinColumn(name = "pet_id")
@OrderBy("date ASC")
private final Set<Visit> visits = new LinkedHashSet<>();
```

逐个概念拆解：

| 概念 | 含义 | 在本项目里的表现 |
| --- | --- | --- |
| `@OneToMany` / `@ManyToOne` | 一对多 / 多对一的表关系 | 一个主人多只宠物；一只宠物一个类型 |
| `@JoinColumn` | **外键列写在"多"的那张表上** | `pets.owner_id`、`pets.type_id`、`visits.pet_id` |
| `CascadeType.ALL` | 保存/删除主人时，级联处理宠物 | 所以 `owners.save(owner)` 就能把新宠物一起存进去 |
| `FetchType.EAGER` | 加载主人时顺便把宠物查出来 | 本项目对 pets、visits 都用了 EAGER |
| `FetchType.LAZY` | 真正用到时才查（默认对集合） | 本项目没用，但这才是更常见的生产选择 |
| `@OrderBy` | 查询结果在内存里排序 | `pets` 按名字排，`visits` 按日期升序 |

注意 `@OrderBy` 不是数据库索引，它只是拼在查询里的 `order by`，**数据量大时可能有性能问题**（尤其对 EAGER 集合。这属于"能跑但不够好"的典型写法）。

再注意 `Owner.getPet(String name)` 用的是 `equalsIgnoreCase`——名字在 Java 层就是大小写不敏感的。

## 3. 仓储：只写方法名，不写 SQL

`src/main/java/org/springframework/samples/petclinic/owner/OwnerRepository.java`：

```java
public interface OwnerRepository extends JpaRepository<Owner, Integer> {

    Page<Owner> findByLastNameStartingWith(String lastName, Pageable pageable);

    Optional<Owner> findById(Integer id);

}
```

你只声明了接口，**没有任何实现类**。Spring Data 在启动时为它生成代理实现，并按方法名解析出查询语义：

```
findBy  +  LastName  +  StartingWith
   |           |             |
 查询动作    实体属性      匹配方式（前缀匹配）
                |
       翻译为：where last_name like 'F%'
```

方法名就是 DSL。常见后缀：`StartingWith`、`Containing`、`GreaterThan`、`OrderByXxxDesc`、`IsNull`。复杂查询再退回 `@Query` 注解写 JPQL——本项目刻意没用，就是为了演示"方法名派生查询"。

顺带说一个细节：`JpaRepository` 本身已经提供了 `findById`，这里又声明一遍，是为了在接口上**显式表达契约**并写清楚返回 `Optional` 的语义（用文档换取可读性）。

`VetRepository` 则是另一种写法：

```java
public interface VetRepository extends Repository<Vet, Integer> {

    @Transactional(readOnly = true)
    @Cacheable("vets")
    Collection<Vet> findAll() throws DataAccessException;

    @Transactional(readOnly = true)
    @Cacheable("vets")
    Page<Vet> findAll(Pageable pageable) throws DataAccessException;

}
```

它继承的是更基础的 `Repository`（不白拿一堆方法，只暴露自己声明的那几个），并显式加上只读事务和缓存（缓存第 5 课讲）。

## 4. 分页：页码差异与 Page 对象

`OwnerController` 里：

```java
private Page<Owner> findPaginatedForOwnersLastName(int page, String lastname) {
    int pageSize = 5;
    Pageable pageable = PageRequest.of(page - 1, pageSize);
    return owners.findByLastNameStartingWith(lastname, pageable);
}
```

- `Page` 不只是数据列表，还带 `getTotalElements()`（总条数）、`getTotalPages()`（总页数）、`getContent()`。
- 分页**发生在数据库**：Spring Data 会执行一条 `limit/offset` 查询加一条 `count` 查询，不是把全表查出来再在内存里切。
- `page - 1`：URL 的页码从 1 开始，Spring Data 从 0 开始。

控制器拿到 `Page` 后，模板就能渲染出"上一页 / 下一页 / 共 N 页"。

## 5. 事务

- 写操作（`save`、`saveAndFlush`）由 Spring Data 自动包在事务里，不需要你手写。
- 只读查询显式标注 `@Transactional(readOnly = true)`（见 `VetRepository`）：告诉数据库这不会改数据，能省下一些开销，也是一份"我承诺不改数据"的声明。
- `saveAndFlush` 与 `save` 的区别：`Flush` 会立刻把 SQL 发给数据库，而不是等事务提交。`PetController` 故意用 `saveAndFlush`，就是为了让唯一约束冲突**当场抛异常**，好被 `catch (DataIntegrityViolationException ex)` 接住。

## 6. 三套数据库脚本，同一份代码

`src/main/resources/db/` 下有 `h2`、`mysql`、`postgres` 三份 `schema.sql` + `data.sql`，靠 `database` 变量切换。这体现了正确的分层观念：**表结构属于部署配置，不属于代码。**

但"唯一约束"这一处，三套脚本用了三种不同写法，这是全项目最值得琢磨的细节：

| 数据库 | 大小写不敏感的唯一约束怎么实现 |
| --- | --- |
| H2 | 列类型用 `VARCHAR_IGNORECASE(30)`，再 `UNIQUE (owner_id, name)` |
| MySQL | 依赖默认的大小写不敏感排序规则（`UNIQUE (owner_id, name)` 即可） |
| PostgreSQL | 没有 `VARCHAR_IGNORECASE`，只能建函数索引 `UNIQUE INDEX ... (owner_id, LOWER(name))` |

而 `PetController` 判断"是不是重名冲突"的方式是**匹配异常文本里的索引名** `unique_owner_pet_name`。这意味着：代码的命运被一份 SQL 脚本里的名字锁死了，改个索引名就会静默失效。

这不是让你照抄的写法，而是让你看到**真实工程的取舍与妥协**。第 6 课的改造题就是重构它。

## 7. 为什么要有 N+1 这一说

`pets`、`visits` 都配了 `EAGER`。假设查列表页有 5 个主人：

```
1 条 SQL 查出 5 个 owner
5 条 SQL 分别查每个 owner 的 pets      <- 这就是 N+1
```

`application.properties` 里的 `spring.jpa.properties.hibernate.default_batch_fetch_size=16` 就是在缓解它：Hibernate 会把"多个父对象的集合"合并成 `where owner_id in (?, ?, ...)` 批量查询，把 N 条压成 N/16 条。

**记住这个结论**：EAGER + 集合 = 列表页的隐藏性能杀手。生产代码通常改成 `LAZY`，再在确实需要的地方用 `join fetch` 或实体图（EntityGraph）精确加载。

### 实验 1（20 分钟）：看真实的 SQL

```
spring.jpa.show-sql=true
logging.level.org.hibernate.orm.jdbc.bind=TRACE
```

重启，访问 `/owners/1`，数一数控制台发了几条 SQL。再访问 `/owners/find` 搜索 `A`，观察列表页的 SQL 条数。

实验完把这两行删掉（记得还原）。

### 实验 2（20 分钟）：证明 N+1 的存在与缓解

先记录实验 1 中列表页的 SQL 条数；然后把 `default_batch_fetch_size` 从 `16` 改成 `1`，重启再数一次。

观察点：同一个页面，SQL 条数变了，页面结果一模一样。**性能问题往往不体现在功能上，只体现在日志和响应时间上。**

### 实验 3（20 分钟）：在数据库里验证你的理解

打开 `localhost:8080/h2-console`，用启动日志里的 `jdbc:h2:mem:<uuid>` 连接，然后执行：

```sql
select * from owners;
select * from pets where owner_id = 1;
select * from visits;
select * from information_schema.columns where table_name = 'PETS';
```

对照你读过的实体代码：`@Column(name = "visit_date")` 对应的列名是不是 `visit_date`？`pets.owner_id` 是不是就是那个外键列？

### 实验 4（20 分钟）：写一个派生查询

在 `OwnerRepository` 里加一个方法：

```java
List<Owner> findByCity(String city);
```

（记得 `import java.util.List;`）然后在 `ClinicServiceTests` 或临时在控制器里调用它，传 `"Madison"`，看是否返回了数据。

你写了一行接口方法，Spring Data 生成了 `where city = ?`。这就是派生查询的威力，也是它的局限——方法名会越来越长，超过三个条件就该换 `@Query` 了。

## 10. 本课要记住的五句话

1. 实体注解描述"对象和表怎么对应"，命名策略负责驼峰与下划线的自动转换。
2. 一对多关系里，外键列永远写在"多"的那一侧。
3. 方法名派生查询是 Spring Data 的招牌能力，但方法名一长就该改用 `@Query`。
4. 分页由数据库完成，`Page` 对象同时带着内容、总数和总页数。
5. EAGER 集合是列表页的性能陷阱，记住"EAGER + 集合 = N+1"。

## 附：自测题答案

1. `@MappedSuperclass` 只把字段下发给子类实体，本身不映射表；`@Entity` 才对应一张真实的表。所以没有 `base_entity` 表，但每张表都有 `id`。
2. 因为配置了 `PhysicalNamingStrategySnakeCaseImpl`，Hibernate 自动把驼峰转成下划线命名。
3. 写在一对多的"一"这一侧、用 `@JoinColumn` 指定"多"那张表里的外键列名；本项目 `pets.owner_id` 由 `Owner.pets` 上的 `@JoinColumn(name = "owner_id")` 决定。
4. 保存主人时会级联保存新宠物，所以 `owners.save(owner)` 一条调用就把宠物一起写库了，不需要单独的 PetRepository。
5. 大致是 `select ... from owners where last_name like ?` 加一个参数 `'F%'`（具体由方言生成）。
6. 都是数据库做的：一条 `count` 查询拿总数，一条带 `limit/offset`（或方言等价语法）的查询拿当前页数据。
7. `saveAndFlush` 立刻把 SQL 发给数据库，唯一约束冲突会当场抛 `DataIntegrityViolationException`；`save` 可能推迟到事务提交。`PetController` 需要在方法内捕获这个异常，所以必须用 `saveAndFlush`。
8. 查 N 个父对象时，为每个父对象各发一条 SQL 去查它的集合，共 N+1 条。`default_batch_fetch_size` 让 Hibernate 把多个父对象的集合合并成 `in (...)` 批量查询，把条数压到大约 N/16。
